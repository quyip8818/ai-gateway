# 账号池反代网关 · 绿地架构

**状态**：本文描述目标架构。仓库已支持空库初始化、账号导入和自动目录、池授权和 Key、文本转发与持久化媒体。实际配置和部署见 [README](../README.md)。可用模型取自部署方配置的执行器，正式发布前要逐一验收真实供应商账号。

本次复用原有 SSE 和媒体运行时，以及专用 jimeng-api、CLIProxyAPI v8 和 kiro2api 的管理协议。专用实例拥有一份上游凭证，网关保存执行凭证和实例绑定。直接接受上游 OAuth 令牌的兼容执行器由网关维护授权及续期。账号并发租约、同账号重授权、模型目录定期刷新与正式供应商验收仍按下文的目标契约推进。

## 1. 产品和上线范围

用户授权自己的上游账号。网关验证并加密保存可接受的凭证，将账号纳入账号池。管理员给调用方签发网关 Key。客户端只知道 **网关地址、网关 Key、可用模型**。网关选择一个已获授权的账号执行，负责续期、隔离、并发、故障状态和用量追踪。

首条成功路径是 **添加账号 → 验证 → 签发 Key → 发出请求**。日常流程允许只导入一个账号；新增第二个账号时自动加入对应的默认池。首版面向自托管团队，每个部署包含一个或多个独立项目。项目是数据和权限边界，项目管理员管理账号及 Key，成员只使用已授权入口并查看自己的调用。

首发验收包含即梦图片和视频、Codex Responses、Kiro 作为上游、Claude Messages。供应商、授权方式和客户端组合逐一验收。计费、支付、促销、跨协议全量转换和跨区域调度留到明确有需求时设计。

## 2. 四个长期架构决定

| 决定 | 设计 | 理由 |
| --- | --- | --- |
| 一个控制面 | 管理 UI、管理 API 和调用入口由同一产品提供。账号凭证由网关的执行服务持有 | 管理员只需维护一个账号池和一个调用 Key 页面。调用方只拿网关 Key。 |
| 两种执行模型 | 文本同步转发及 SSE，媒体进入持久化任务队列 | 流式请求一旦输出就不能换号补流；异步任务需要在重启后继续查同一上游任务。 |
| 先单部署，再按负载拆进程 | Go 模块化单体、React、PostgreSQL。API 和 worker 从同一个代码库构建，初期可同进程运行 | PostgreSQL 统一存储权限、任务和租约；吞吐确有瓶颈时独立扩容执行进程。 |
| 鉴权、协议、上游分别扩展 | 协议模块决定客户端请求格式，适配器声明该模式支持哪些授权、模型和操作 | Claude Code 是客户端，Kiro 可以是上游。支持 Messages 不代表支持 Claude 的订阅凭证。 |

主链路和信任边界如下。适配器只拿本次所选账号的凭证。状态和用量通过内部接口回写。

### 开源参考对应的决定

- **jimeng-free-api-all** 的账号池和调用密钥分离，印证了 Cookie 导入之后再签发调用 Key 的产品路径。采纳其账号状态、到期和冷却的交互。 [账号池源码](https://github.com/zhizinan1997/jimeng-free-api-all/blob/main/src/lib/account-pool.ts) · [调用接口](https://github.com/zhizinan1997/jimeng-free-api-all/blob/main/API.md)
- **Sub2API** 的账号、分组、Key 分属不同实体。采纳池隔离、密钥授权和运行状态的边界。首期按账号归属单池设计，多个调用者通过权限复用一个池。 [账号模型](https://github.com/Wei-Shaw/sub2api/blob/main/backend/ent/schema/account.go) · [分组模型](https://github.com/Wei-Shaw/sub2api/blob/main/backend/ent/schema/group.go) · [Key 模型](https://github.com/Wei-Shaw/sub2api/blob/main/backend/ent/apikey/apikey.go)
- **Sub2API Kiro、kiro2api** 把登录、刷新、状态验证和转发作为独立能力。远程部署的首选流程是适用的设备授权，组织方式才要求组织入口和必要区域。 [Sub2API Kiro](https://github.com/xiangking/sub2api-kiro/blob/main/README.md) · [kiro2api 账号管理](https://github.com/xwteam/kiro2api/blob/main/docs/en/USAGE.md) · [Kiro 官方认证](https://kiro.dev/docs/getting-started/authentication/)
- **CLIProxyAPI** 分开处理 OAuth 会话、凭证导入、账号验证和客户端 Key。采纳这些资源边界，诊断测试固定使用选中的账号。 [CLIProxyAPI 管理 API](https://github.com/router-for-me/CLIProxyAPI/blob/main/docs/management-api-v8.md)

参考行为和接口设计。确需引入第三方实现时，再按选定版本核对许可证与分发义务。

## 3. 统一领域模型

| 实体 | 含义与不变条件 |
| --- | --- |
| 项目 | 管理和数据隔离边界。所有池、账号、调用 Key、请求、任务和资产均属一个项目。带 ID 的对象查询必须同时约束项目和调用人权限。 |
| 账号池 | 隔离一组可互换的上游账号。每个池只有一个供应商和一个授权边界。首次验证成功时创建该供应商、授权边界下的默认池。个人池绑定授权人，团队池要求该上游授权允许团队使用。 |
| 上游账号 | 供应商验证出的稳定身份以及授权资源。一个账号同时属于一个池。禁止把同一个刷新凭证在多个运行账户中并行续期。 |
| 账号凭证 | 当前凭证密文或已授权的隔离运行时引用。凭证替换保持账号 ID，前提是验证出的身份和授权资源一致。 |
| 调用 Key | 管理员为项目成员或项目自动化签发，权限限定到账号池与操作。Key ID 稳定，轮换仅更换密钥与前缀。 |
| 公开模型 | `<pool-slug>/<adapter-model-id>`，在项目及协议下可解析为一个池内模型。显示名称独立于稳定 ID，改名不影响客户端配置。 |

**目录、权限、可用性分别判断。** 管理页可看到账号发现的模型。客户端模型列表以 Key 授权和适配器协议能力过滤；短期故障或冷却不删除模型。请求时再次检查可用账号并返回明确状态。多个池的同名上游模型有不同公开 ID，避免路由选择隐式跨供应商。

目录由账号能力快照投影。首版采用默认稳定 ID，没有手写路由表。适配器确认模型下线后不再接受新调用。请求与任务记录本次实际解析出的池、账号、操作、上游模型和适配器版本；任务恢复使用该快照。日后确有客户自定义模型名的需求，再增加显式别名资源。

账号去重使用适配器验证出的稳定标识，组合供应商、授权身份和工作区或组织资源。旋转凭证的身份在整个部署内只有一个归属项目。重复导入只提示凭证冲突，不泄露归属项目。Cookie 或令牌指纹只用于识别同一份上传内容。供应商无法提供稳定身份时，管理员显式确认其归属，轮换时重新验证。个人授权默认只允许授权人使用，池的共享范围受授权方式和账号的授权范围约束。

## 5. 控制台与最少输入

导航为 **账号、调用密钥、使用、记录**。项目选择仅在多项目时显示。项目管理员管理池、账号和 Key；成员获得已授权接入入口和自己的调用记录。

| 页面 | 默认内容和操作 | 何时增加字段 |
| --- | --- | --- |
| 账号 | 按供应商筛选。账号名、状态、最近验证、可提供的额度。主动作「添加账号」。 | 按适配器展示一种导入或授权方式。只有组织登录确实需要时填写组织入口/区域。 |
| 导入或授权 | 选供应商后只显示 Cookie、文件选择或继续授权。名称默认从脱敏身份生成。验证通过后显示模型能力和「创建调用 Key」。 | 导入失败时显示缺失项或重新授权。额外分池、暂停、并发上限放在账号详情。 |
| 调用密钥 | 名称、前缀、授权池、状态、最近调用。明文在签发或轮换完成后显示一次。 | 只有一个可选择的池时默认选中，授权前仍展示该池；多个池明确勾选。范围、有效期、配额上限按需配置。 |
| 使用 | 按客户端展示已授权的接入配置与可选模型。网页创作默认只显示提示词和生成按钮。 | 多模型才展示选择器。画幅、时长、参考图按已验证模型能力出现。API 示例折叠。 |
| 记录 | 请求 ID、模型、状态、时长，支持失败或待核验筛选。 | 展开上游尝试、账号掩码、用量来源和失败建议。媒体产物到期后显示任务记录与到期状态。 |

启动配置管理数据库、服务地址、加密主密钥和资产存储。普通账号表单没有上游 Base URL、共享额度域、通用区域框和媒体能力 JSON。网页生成依项目登录授权，CLI 和脚本依调用 Key 授权。浏览器会话与调用 Key 使用不同验证入口。

## 6. 代码边界与适配器接口

| 模块 | 写入内容及依赖 |
| --- | --- |
| `identity` | 用户、项目、会话和 Key。为下游导出统一的调用主体及访问范围。 |
| `accounts` | 导入任务、授权会话、身份去重、凭证版本、可用性和能力快照。编排供应商适配器与保险库。 |
| `providers` | 每个授权方式的解析、验证、续期和执行。供应商字段只在这里有语义，持久化格式显式版本化。 |
| `catalog` | 从能力快照投影公开模型，为指定协议和授权范围解析稳定 ID。 |
| `scheduler` | 候选策略、会话粘性、容量与租约。只接触账号状态和能力，不读取凭证明文。 |
| `protocols` | 实现 Responses、Messages 和媒体 JSON 契约。映射基础事件和错误，调用相应执行服务。 |
| `text`、`media` | 编排协议执行。文本保持流式，媒体持久化任务、租约、重试和产物。 |
| `storage`、`metering` | 对象存储、请求/尝试记录、用量和审计。通过接口服务上层。 |

Go 中按能力提供小接口，适配器只实现自己支持的操作：

- `AccountAuthorizer`、`CredentialImporter`。启动授权或解析文件，提交经过验证的身份与密文材料。
- `AccountProbe`、`CredentialRefresher`。检查身份、模型和额度。返回可重试与需重新授权状态。
- `TextExecutor`。支持明确声明的协议、流和取消。原生协议尽量转发原始事件，转换器只支持由契约测试覆盖的交集。
- `MediaExecutor`。提交、轮询、取回成品。显式声明上游幂等、取消与查询能力。

适配器结果至少区分 **明确未提交、已接受、受理未知**，独立标注已写入客户端事件、上游 ID、错误类型、重试时间和用量置信度。启动时注册适配器并校验声明，因配置或可用授权缺失的能力不上架。任意用户输入不能决定上游主机、运行时命令或文件路径。CLI/ACP 模式按账号隔离进程、目录与会话，工具权限按实际支持能力约束。

### 当前实现的扩展入口

当前代码用 `providers.Adapter` 注册供应商的凭证解析、OAuth 资格、专用执行器和模型目录分类。账号池持久化供应商 ID，上游账号存储执行协议和凭证，账号模型存储已验证的模型能力。文本和媒体按协议选路，账户和 Key 不维护供应商分支。兼容 Responses、Messages 或现有媒体契约的供应商可用 `providers.json` 注册。现有接入默认按项目、供应商和授权归属建立账号池。

## 7. 运行规则、并发和恢复

### 账号状态与调度

管理状态 `active / paused / revoked` 与健康状态 `verifying / ready / cooldown / reauthorize / unavailable` 独立。刷新或验证不能把管理员已暂停的账号改回可调度。

1. 校验调用主体，解析协议、操作、公开模型和目标池。账号池授权与上游可共享范围取交集。只在该交集里筛选同一操作可用的账号。
2. 排除需要重新授权、冷却中、用量明确超限或并发已满的账号。优先使用合法的会话绑定，再在可用账号中择空闲容量；并列时轮转。会话按项目、Key、池和客户端会话隔离。
3. 占用执行许可前原子确认账号状态和槽位。租约有过期和单调版本，耗时操作在事务外执行，迟到结果无法覆盖新持有者的数据。初期按账号行锁分发槽位，用数据库时间判断到期。运行中的流和 worker 续租。续租失败时停止发起新的上游操作；已经发送的操作按受理状态收尾。
4. 拒绝时返回可区分的「模型不支持、无授权、无可用账号、池繁忙、上游限流」。上游限流按其适用范围进入冷却，不通过更换账号规避供应商的限额。用户取消、超时和进程结束均释放本地容量。

### 凭证更新

同账号同一时刻只允许一个刷新调用。先记录待执行的凭证版本和刷新租约，随后向上游刷新。只有当前版本和租约都吻合才写入新密文。管理员发起的重授权、替换与刷新使用同一版本约束。加密主密钥轮换通过密钥版本重加密。上游凭证泄露时暂停调度、在上游撤销并重新授权。

**本地租约保护数据库写入，不能保证上游只收一次。** 刷新结果不明时暂停新的刷新与调度，按供应商认可的方式验证恢复，必要时重新授权。收到 401 时，仅在没有已接受结果的情况下尝试一次受控刷新；已开始的流保持失败记录，成本和用量按实际所知登记。

### 文本流

调用授权通过后生成请求 ID，再获取账号和本次尝试 ID。只有适配器明确证明请求没有送达、且客户端尚未收到流事件，才允许在同一个授权池内切换一次等价账号。取消向上游传播，无法确认远端取消时以本地取消和上游结果未知结束。流开始后保留原账号，错误以目标协议可表达的方式告知客户端。

### 媒体任务

状态为 `queued → submitting → running → finalizing → succeeded`，另有 `failed`、`canceled` 和 `submission_unknown`。图片瞬时返回时可直接进入 `finalizing`。

- 创建任务时，在事务中保存请求记录、输入摘要、已授权素材引用及幂等键。调用 Key 或成员主体的稳定 ID 组成幂等范围。相同键与摘要返回同一任务，摘要变化返回冲突。
- worker 持久化提交尝试后才向上游发送。提交结果未知时保留尝试和账号，不自动改用其他账号。受理未知进入待核验状态，保留任务 ID 与上游尝试用于排查。提交 worker 认领任务时清除排队输入，查询与交付使用已记录的上游任务 ID。
- 已接受后始终用记录里的账号轮询和下载。账号暂停停止认领新任务，已受理任务允许排空。账号授权撤销则停止上游访问，明确提示需要核验。Key 撤销即时拒绝新的调用和读取；已受理任务由服务端按项目授权完成。
- 排队任务可原子取消。对已送达的任务，只在上游确认撤回后标记取消。如果适配器无法取消，页面说明原因并继续跟踪。用户关闭页面不改变任务状态。
- 下载后先把产物写入受控存储，再事务确认任务完成。崩溃时可以重新交付；无引用文件由清理任务回收。下载只对有当前 ACL 的调用方开放，避免暴露上游签名地址或会话。

## 8. API 设计

控制台通过 `/console/v1/session` 管理登录会话。首次部署由启动命令创建管理员，密码存储为 Argon2id 摘要。项目 API 使用 `/console/v1/projects/{project}`，校验同源写操作、会话和项目角色。下表省略项目前缀。失败统一返回可处理的错误代码、消息与请求 ID。

| API | 最少输入及响应 |
| --- | --- |
| `GET /providers` | 返回可用授权方式、界面可显示字段、能力和发布状态。供产品表单渲染。 |
| `POST /account-enrollments` | 供应商、授权方式；按需携带 Cookie、文件或组织参数。返回任务 ID、状态和适用的授权步骤。 |
| `GET /account-enrollments/{id}` | 发起人在有效期内查询验证状态。成功返回账号与池 ID，失败返回脱敏原因。 |
| `GET /accounts`、`GET /accounts/{id}` | 脱敏账号、池归属、支持模型、额度来源和状态。仅管理员使用。 |
| `PATCH /accounts/{id}` | 更名、暂停、恢复或移动到同供应商同授权边界的池。重授权通过导入任务指定目标账号。 |
| `POST /accounts/{id}/verify` | 对单账号执行轻量验证。推理测试需要明确选择。 |
| `GET /pools`、`GET /catalog` | 供管理面选择可授权池、展示能力与已发布模型。普通成员只得到有权限的投影。 |
| `POST /pools` | 高级操作，按已验证的授权边界创建额外账号池。默认池自动创建。 |
| `GET /keys`、`POST /keys`、`PATCH /keys/{id}` | 读写 Key 名称、状态、授权池与操作。仅创建时返回原文。 |
| `POST /keys/{id}/rotate` | 保持 Key ID 和授权范围，原子切换摘要并返回新密钥一次。 |
| `GET /requests`、`GET /requests/{id}` | 游标查询脱敏请求、尝试、用量及关联任务。 |
| `/media/assets`、`/media/jobs` | 网页会话入口，复用调用面的上传、提交、查询、取消和下载服务。 |

供应商 OAuth 回调使用单独的注册路径。对应状态由服务端绑定项目、发起人、供应商和到期时间，验证适用的 state/PKCE。回调只消费一次，轮询本身可重复。凭证和临时导入原文无读取或导出接口。

| 调用 API | 契约 |
| --- | --- |
| `POST /openai/v1/responses`、`GET /openai/v1/models` | Codex 入口，采用 Responses 结构与原生 SSE。 |
| `POST /anthropic/v1/messages`、`GET /anthropic/v1/models` | Claude Code 入口。对外仍是 Messages，实际供应商由公开模型确定。 |
| `POST /anthropic/v1/messages/count_tokens` | 只有原生支持或已验证等效的模型开放。 |
| `POST /media/v1/assets`、`POST /media/v1/jobs` | 先上传可选参考图；创建时传公开模型、生成操作、提示词、可选媒体参数和幂等键。 |
| `GET /media/v1/jobs/{id}`、`POST /media/v1/jobs/{id}/cancel` | 查询与取消。说明取消是本地停止还是已确认撤回。 |
| `GET /media/v1/jobs/{id}/artifacts/{artifact}` | 按项目与调用者权限交付产物。 |

OpenAI 与媒体入口使用 `Authorization: Bearer <网关 Key>`，Anthropic 入口接受 Messages 客户端使用的 `x-api-key` 或 Bearer。两者同时存在且值不一致时拒绝请求。创建媒体任务返回任务 ID、状态查询地址和 `202 Accepted`；幂等重试返回同一个任务。模型、样例及文档从同一能力投影生成。客户端仍需用实际版本验证鉴权头、错误形状、工具调用和流结束。

## 9. 最小数据库和数据边界

新库用 DDL 约束跨项目关系。所有对外可引用对象都使用不透明 ID。唯一键和索引服务于去重、认证、调度及按时间查询；额度快照允许未知。

| 表或归属 | 最少字段和核心约束 |
| --- | --- |
| `projects`、`users`、`project_members`、`web_sessions` | 项目及状态、用户身份、项目角色、会话摘要及有效期。成员在同项目唯一。 |
| `account_pools` | 项目、供应商、授权边界、共享类型和个人池所有者、稳定 slug、名称和状态。同项目 slug 唯一。 |
| `upstream_accounts` | 项目、池、执行协议、上游地址、执行凭证密文、可续期账号的独立刷新凭证密文、凭证去重摘要、验证时间和账号状态。稳定身份去重、冷却与并发上限属于后续调度工作。 |
| `account_enrollments` | 项目、发起人、授权方式、一次性状态摘要、临时密文、目标账号、到期及脱敏结果。导入与 OAuth 共用生命周期。 |
| `account_models` | 账号、公开模型、供应商模型、操作和能力载荷。同账号、操作和模型唯一。目录据此投影，媒体任务绑定入队时选中的模型记录。 |
| `access_keys`、`key_grants` | 项目、Key ID、持有人、名称、前缀、摘要、有效期/撤销时间、池及操作。轮换更新同一个 Key 的摘要。 |
| `execution_leases` | 账号、用途、持有者、版本、失效时间。支撑文本槽位、媒体执行与刷新。按账号和失效时间索引。 |
| `requests`、`attempts`、`usage_records` | 请求主体、公开与上游模型、池、实际账号、适配器版本、结果及耗时；每次尝试的提交状态、上游 ID、用量、单位和来源。用量以尝试和指标幂等写入。 |
| `media_jobs`、`assets`、`job_assets` | 任务执行快照、临时排队输入、状态、幂等键/摘要、上游任务 ID、租约与进度；独立的对象引用、大小、类型、过期时间；素材/产物角色和顺序。 |
| `audit_events` | 项目、操作者、对象、动作、时间、请求 ID。只收脱敏管理元数据。 |

池和账号采用同项目的复合外键。媒体任务的素材必须同项目且对提交主体可读。软归档仍被历史引用的账号和 Key，仅删除按策略到期的凭证材料和素材。数据库中没有重量级请求抓包、Cookie 原文、刷新令牌明文、浏览器指纹、价格表或余额账本。

**保存期限独立定义。** 授权中间数据成功或到期即清理。文本提示词和响应体默认不落库。媒体输入在 worker 认领或任务取消时清理。成品按项目保留期淘汰。任务元数据、用量和审计可按单独期限保存。上游明确返回的用量才标为上游报告，估算和未知单独标注。日志与监控禁止凭证原文和用户请求正文。

## 10. 部署、验证和实施顺序

**初始部署**。Go 服务、PostgreSQL、TLS 入口和受控媒体存储。单节点可用私有目录，多节点再启用共享对象存储并独立扩容 worker。加密使用版本化主密钥和统一保险库接口。备份应同时演练数据库、媒体索引和正确的密钥版本恢复。管理口独立限流，调用口限制请求体、流持续时间和项目并发。上游主机由适配器配置，成品下载只允许适配器登记的目的地。

**可测性**。用合成凭证和模拟上游测状态机，用经过批准的测试账号验收供应商。重点反复注入提交超时、刷新超时、进程重启、过期租约、限流、取消和对象存储失败。每次试验都用请求 ID 核对所选账号、是否允许重放、最终产物和用量。跨项目访问测试覆盖账号、Key、媒体和诊断接口。

| 阶段 | 实现交付 | 通过条件 |
| --- | --- | --- |
| A. 绿地骨架 | 初始化新数据库；实现项目、Key、保险库、导入任务、默认池和模块契约。模拟适配器串起控制台 | 无需配置空白路由即可从导入走到签发 Key。越权、密钥明文泄露、重复导入和轮换回归通过。 |
| B. 即梦闭环 | Cookie 验证、图片与视频、成品预览、恢复和到期清理 | 获授权账号完成图片、视频和取回产物。重启后在原账号继续轮询，受理未知不会重复生成。 |
| C. 文本执行 | Responses 与 Messages，Codex 授权、Kiro 导入/授权及续期，并按适配器选择能力 | 各组合真实首条流式请求成功。工具事件、取消、授权失败、冷却和刷新并发通过契约测试。未通过的能力不出现在模型列表。 |
| D. Claude 与上线准备 | 已授权 Claude 上游、Claude Code 配置、追踪与容量测试、最小运维面 | 可区分 Claude 与 Kiro 来源。通过长流、发版重启、备份恢复和撤销 Key 演练。 |
| E. 按需扩展 | 实测后选择水平扩容、可配置别名、批量导入和独立统计 | 以实际容量和使用频率决定。新增适配器无需改 Key、账号池、任务主流程。 |

上线信号包括首条成功请求耗时、导入完成率、每池可用账号与并发、上游首包时长、待核验任务数、授权失效恢复时长、用量覆盖率。验证测试通过前，界面可以展示“该能力待验收”，避免展示无法调用的配置。

开发阶段用空库做首个版本的初始化与端到端验收。当前仓库中的原型实现不作为重写接口或数据模型的约束。
